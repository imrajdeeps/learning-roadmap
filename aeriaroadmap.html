Read this first

The backend is where you're actually equal, and it's most of the work. Raj brings a real head start on the frontend and Sakshi brings a real head start on structured, typed, object-oriented design — but NestJS, Hasura, PostgreSQL, GraphQL codegen and the RS256 auth chain are zero for both of you. That's roughly 65% of the difficulty of this platform, and it's why "same track, in sync" is the right call: you're only asymmetric for about a week.

The stack doc is a snapshot, and several pins are behind the support line. This matters because you'll hit it on day one when you npm install and get something newer than the doc says. Learn the current version, then learn what the pinned one does differently — that delta is exactly what a new team member is expected to know.

What each of you brings

You are not the same learner, and pretending otherwise wastes both your advantages. Week 1 is deliberately asymmetric; from week 2 you converge.

Raj — strong JS, good React, zero backend

Transfers directly: components, hooks, state, JSX, the npm ecosystem, DevTools debugging. Most of the Aeria frontend is libraries you haven't used yet, not concepts you don't have — TanStack Query, Tailwind, Formik/RHF, App Router. You'll absorb those in days, not weeks.

Your actual gaps: TypeScript's type system as a design tool (not just annotations), server-side thinking, SQL, and the whole "one request touches five services" mental model. Also: React Server Components are genuinely a different model from the React you know — resist assuming it's just React with extra steps.

Your job in the pair: teach Sakshi JavaScript and React. Teaching is not charity here — explaining closures and the event loop out loud is what will finally make your own understanding airtight, and you'll discover gaps you didn't know you had.

Sakshi — strong C++, new to JS, zero backend

Transfers directly, and more than you'd expect: static types, generics, interfaces, classes, inheritance, composition, references vs values, and algorithmic thinking. TypeScript will feel like coming home. NestJS will feel natural to you before it does to Raj — modules, dependency injection, decorators and constructor injection are Spring/OOP patterns, not JavaScript patterns. Expect to lead the backend weeks.

Your actual gaps: JavaScript's dynamic, single-threaded, event-loop-driven runtime. The things with no C++ analogue are where you'll lose time — closures, prototypes, this binding, truthiness coercion, and above all the async model. Budget week 1 heavily for these.

Your job in the pair: hold the line on type rigor and design. Raj's instinct will be to ship fast and loose; yours should be to ask "what's the interface?" That tension is productive — it's why pairing beats two people working alone.

C++ → TypeScript, for Sakshi

The fastest path in is to map what you know rather than start from zero. What transfers is in the top half; the bottom half is where your intuitions will actively mislead you.

C++ concept TypeScript equivalent Note
template<typename T> function f<T>(x: T) Nearly 1:1. Generics are structural, not instantiated per-type.
Abstract base class / pure virtual interface / abstract class Interfaces are compile-time only — they vanish at runtime.
struct of fields type / interface TS typing is structural, not nominal: same shape = same type, no inheritance needed.
std::optional<T> T | undefined, T? Union types are more general than optional. strictNullChecks is your -Wall.
enum class union of literals (preferred) or enum Prefer 'a' | 'b' over TS enum — the ecosystem does.
const correctness readonly, as const Weaker than C++ — shallow, and erased at runtime.
std::vector, std::map T[], Map, plain objects Plain objects are used as maps constantly. Get comfortable with that.
Constructor injection / DI frameworks NestJS providers + @Injectable() This is your edge. Nest's DI is a familiar pattern wearing decorators.
RAII, destructors, manual memory — (no equivalent) GC handles it. Your ownership instincts have nowhere to go — let them go.
Threads, mutexes, std::async Single-threaded event loop The biggest shift. No data races, but also no blocking — ever. await yields, it does not block a thread.
Function pointers / lambdas w/ capture list Closures (implicit capture by reference) JS captures the variable, not the value, and captures everything automatically. Source of real bugs.
Static typing enforced at runtime Types are erased TS gives you zero runtime guarantees. This is why Zod / class-validator exist — they're the runtime half of the type system.
this = the object this = call-site dependent Arrow functions capture lexical this; regular functions don't. Just use arrows.
Strong typing at comparisons Coercion: == vs === Always ===. Learn the falsy set: 0 "" null undefined NaN false.

Sakshi's week-1 reading order: TS for OOP programmers (written for exactly your background) → javascript.info parts 1–2, skipping syntax you already know from C++ → the event loop → closures. Do not skip the last two.

How to actually pair

"In sync" fails by default unless you give it structure. This is the rhythm that works at 40 hrs/week; adapt the times, keep the shape.

Daily (8 hrs): 30 min stand-up — what each of you is doing, what's blocking. Then a 3-hour pair block on the hardest thing of the day, rotating driver/navigator every 25 minutes. Then ~4 hrs solo on your own track. End with a 20-minute teach-back: each of you explains one thing you learned, out loud, to the other. The teach-back is not optional — it is the single highest-signal detector of "I thought I understood this."

Weekly: Friday afternoon demo of whatever runs, then a 30-minute retro (what was slower than expected, what to change), then update DECISIONS.md and DELTAS.md together.

On the capstone: each of you owns services but reviews the other's — no code merges without the other reading it. Swap ownership at the start of week 7. Forcing yourself into unfamiliar code is the only reliable way to guarantee neither of you ends up with a blind spot.

The one rule: if you're stuck for more than 40 minutes alone, you must pull the other person in. Silent struggling is where paired learning goes to die.

Hasura is the most distinctive thing about this platform and the least transferable — almost nothing you've read online prepares you for it. Give it the full week.

Docs: Hasura v2 docs · Metadata format reference · Permissions

The signature pattern: Hasura inside the service

The highest-leverage week · codegen · typed SDK · one container, two processes

This is what makes Aeria Aeria. The stack doc names it the single highest-leverage concept on the platform, and the codegen workflow as the thing that blocks nearly all backend work if you can't run it. Get both airtight.

Docs: GraphQL Code Generator · Auto-apply migrations image
Done when: docker compose up gives you a service that self-migrates, and changing a column propagates to a TypeScript compile error in under two minutes.

Auth end to end & the cross-cutting library

Swap capstone ownership this week · RS256 · guards · Redis · S3 · SQS · Sentry

The RS256 chain is Aeria's spine: ms-auth issues a token, Nest guards validate it, and Hasura consumes the same token as session variables for row-level rules. One token, two enforcement layers.

Done when: a single login token works against all three services, Hasura row-level rules enforce tenancy from its claims, and you can each explain the full chain from password to WHERE clause.

Integrate, test, ship

The whole system up with one command · tests · AWS awareness · write it up

Wire the week-3 frontends to the real services and make the whole thing start with one command. Then prove it works and write down what you learned.

Done when: docker compose up brings up the whole platform, a user can log in on one frontend and see permission-scoped data on both, and each of you can present the other's half.

The capstone: "Mini-Aeria"

Deliberately a faithful miniature, not a simplification — same shape, three services instead of fourteen. Start it in week 4 and grow it every week after.

Suggested domain: visitor management for an office building, mirroring Aeria's real ms-auth / ms-core / ms-visitor split. Pick something else if you prefer — keep the shape.

Component Owns Exercises
ms-auth Users, credentials, RS256 signing, JWKS bcrypt, asymmetric JWT, refresh tokens, the claims namespace
ms-core Orgs, sites, members (the central service) Multi-tenancy via relationship-traversing Hasura permissions
ms-visitor Visitor passes, check-in/out Event triggers, SQS, S3 (visitor photos), cross-service calls to ms-core
admin-dashboard Vite SPA + react-router 7 3 base URLs, TanStack Query, Redux Toolkit, Tailwind, charts
web-checkin Next.js App Router RSC, Apollo Client → Hasura directly, graphql-ws subscription

Hard constraints — these are what make it faithful: each service is one container running its own Hasura + its own Postgres database. No API gateway — frontends hold separate base URLs per service. All Nest reads go through the generated typed SDK, not raw SQL. One RS256 token is validated by Nest guards and consumed by Hasura as session variables. Schema changes only ever happen through hasura migrate + metadata YAML in the repo.

Traps to sidestep

Splitting frontend and backend between you

You already chose not to, and it's the right call — but the temptation returns hard around week 5 when Hasura is confusing and Raj could be "usefully" building UI instead. Resist it. The person who skips the Hasura week becomes permanently dependent on the other for half the platform.

Sakshi trying to write JavaScript like C++

Classes for everything, defensive copying, manual iteration instead of .map(). It compiles and it's readable to you and it will look alien in review. Lean on Raj hard for idiom in weeks 1–3.

Raj assuming Server Components are "just React"

They aren't — the module-graph boundary is a genuinely new model, and existing React intuitions actively mislead here. This is the one place where Raj's experience is a liability rather than an asset.

Using the Hasura web console

Worth repeating because it's the most expensive mistake available: changes made on :8080 write nothing to disk, are invisible to Git, and are destroyed by the next metadata apply. Across 14 services this is how you get 14 divergent schemas. Only ever hasura console.

Learning the pinned versions instead of the current ones

Next 14 is EOL, Hasura v2.37 is outside every support window, ESLint 9 goes EOL next week. Learn current, document the delta. Knowing "we're on X, current is Y, here's what differs" is exactly what makes someone useful on day one.

Two months of learning and nothing that runs

The capstone starts in week 4, not week 8. Something must be running and demoable at every Friday demo, even if it's ugly. A working three-service system beats a comprehensive set of notes by an enormous margin.

Two files that will matter more than your code

DELTAS.md — every place the Aeria pin differs from the current version, and what breaks. You'll build it incidentally over 8 weeks, and it's the most useful document a new team member can arrive holding.

DECISIONS.md — three lines per architectural choice: what you picked, what you rejected, why. When someone asks "why does a read go through Hasura here but a Nest endpoint there?", this is the file that means you have an answer instead of a guess.
